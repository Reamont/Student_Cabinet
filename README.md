# Пульс Кампуса

Личный кабинет студента вымышленного «РТУ МЕМРЭА» для проекта «Цифровой деканат будущего».

**Конкурсный прототип. Не является официальным сервисом вуза. Все данные вымышлены.**

На главной — ближайшее занятие, изменения расписания, дедлайны, обращения и «План на сегодня». Студент может создать обращение, проверить данные перед отправкой, отслеживать историю, ответить на уточнение и читать персональные уведомления. Сотрудник меняет статусы через защищённую административную панель Django.

## Стек и требования

Python 3.12+, Django 5.2 LTS, серверные шаблоны, небольшой собственный CSS/JS, PostgreSQL в production. SQLite используется для локальной демонстрации. Django выбран ради встроенных форм, CSRF, сессий, миграций и административной панели; отдельные SPA и API для этого объёма не нужны. Внешнего ИИ API нет: план собирает существующие записи текущего студента по правилам.

Версии прямых и транзитивных зависимостей зафиксированы в `requirements.lock`. Сведения о доступных версиях получены из официального PyPI; исходные ссылки — в [лицензиях](docs/licenses.md).

## Локальный запуск

Из корня проекта:

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.lock
bash scripts/dev.sh
```

Скрипт подготавливает миграции, демонстрационные данные и статику, затем запускает сервер на порту 8000. При первом запуске генерируются уникальные локальные секреты и пароли в игнорируемом `var/dev.env`; повторный запуск их не меняет. Откройте локальный адрес, напечатанный Django, в браузере этой машины. Облачная среда не означает публикацию в Интернете.

Тестовые логины: `alisa`, `maks`. Сотрудник: `curator`, вход через `/admin/`. Сгенерированные локальные пароли доступны владельцу в `var/demo-access.txt` (права 0600); окружение хранится в `var/dev.env`. Передавайте доступ приватно. Не прикладывайте эти файлы к исходникам или скриншотам. Публичной регистрации и восстановления пароля нет.

Чтобы выполнить команды отдельно:

```sh
set -a
. var/dev.env
set +a
.venv/bin/python manage.py migrate --noinput
.venv/bin/python manage.py seed_demo
.venv/bin/python manage.py collectstatic --noinput
.venv/bin/python manage.py runserver 127.0.0.1:8000 --noreload
```

`seed_demo` при первом создании аккаунтов требует `DEMO_STUDENT_PASSWORD`, `DEMO_SECOND_PASSWORD`, `DEMO_STAFF_PASSWORD`; Django проверяет длину от 12 символов и слабые пароли. Используйте разные случайные значения. Повторное заполнение не сбрасывает пароли и не удаляет заявки. Для актуального расписания команда добавляет отсутствующие демонстрационные занятия текущей и следующей недели; дата «сегодня» всегда определяется в `Europe/Moscow`. Старые данные не выдаются за текущие. Ранее созданные дедлайны и даты экзаменов не сдвигаются повторным seed: это предотвращает незаметное изменение обязательств. При длительной демонстрации проверяйте их актуальность отдельно.

## Конфигурация

Пример без рабочих секретов: [.env.example](.env.example). Приложение читает переменные процесса; само `.env` не загружает. Compose читает выбранный файл через `--env-file`, локальный скрипт загружает `var/dev.env`.

| Переменная | Назначение |
| --- | --- |
| `DJANGO_SECRET_KEY` | Обязательный случайный секрет сессий и подписей, не менее 50 символов для production |
| `APP_ENV` | `production` включает production-ограничения |
| `DJANGO_DEBUG` | Только локально `1`; production принудительно отключает отладку |
| `DATABASE_URL` | PostgreSQL в production; без значения локально используется `var/campus.sqlite3` |
| `DJANGO_ALLOWED_HOSTS` | Домены без схемы через запятую; добавьте `localhost` для healthcheck |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Полные HTTPS origins через запятую |
| `DEMO_STUDENT_PASSWORD` | Первый пароль `alisa`; требуется при первом создании |
| `DEMO_SECOND_PASSWORD` | Первый пароль `maks`; требуется при первом создании |
| `DEMO_STAFF_PASSWORD` | Приватный первый пароль `curator`; не публикуется |
| `POSTGRES_PASSWORD` | Только Compose: URL-safe пароль контейнера PostgreSQL |

Production не стартует без PostgreSQL и `DJANGO_SECRET_KEY`. Приложение доверяет `X-Forwarded-Proto` только при production-настройке: порт Gunicorn должен быть закрыт извне, nginx обязан **перезаписывать** этот заголовок.

## Проверки

После загрузки окружения:

```sh
.venv/bin/python manage.py check
.venv/bin/python manage.py makemigrations --check --dry-run
.venv/bin/python manage.py test
.venv/bin/python manage.py collectstatic --noinput
```

Тесты используют отдельную тестовую БД. Проверяются вход и выход, разграничение данных двух студентов, серверное назначение владельца и статуса, валидация и повторная отправка обращений, CSRF и раздельное прочтение уведомлений. Фактические результаты и браузерные доказательства записываются в [отчёте](docs/process-report.md); команды выше сами по себе не означают, что проверка уже выполнена.

5 ноября 2026 выполнены **31/31 теста на SQLite и 31/31 на PostgreSQL 17**, чистые миграции и повторный seed, Docker-сборка и запуск Gunicorn, `check --deploy` без замечаний и сохранность данных после реального перезапуска. В Chromium пройдены 13 групп сценариев, включая обоих студентов, сотрудника и девять экранов при 360 px. Публичный HTTPS и доступность из России не проверены.

Браузерный smoke и экспорт отчёта — отдельные инструменты разработки:

```sh
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python scripts/browser_smoke.py
.venv/bin/python scripts/export_report.py
```

Они используют системный Chromium по пути `/usr/bin/chromium`; это путь проверенного Linux-окружения. Smoke требует работающий `scripts/dev.sh`, читает локальные credentials без вывода и создаёт новую вымышленную заявку; повторные запуски учитываются лимитом входа. Exporter создаёт `docs/process-report.html` и `.pdf` из Markdown с настоящими PNG. Эти зависимости не нужны web-серверу.

Для проверки чистого окружения используйте отдельный временный каталог и пустую БД, затем те же `pip install`, `migrate`, `seed_demo`, `collectstatic`, `test`. Не удаляйте существующую БД ради такой проверки. Для PostgreSQL задайте URL отдельной тестовой базы, владельцу нужны права создавать тестовую БД.

## Публичное HTTPS-развёртывание

Подготовлен вариант для **отдельного VPS Ubuntu 24.04 в российском дата-центре**, например Selectel, с постоянным диском. Выбор — техническая рекомендация, не обещание доступности или конкретной цены. Хостинг, домен и аккаунт владельца не предоставлены; сайт не опубликован. Проверка из сети России без VPN ещё необходима.

Подробная последовательность, резервное копирование и обновление — в [deploy/README.md](deploy/README.md). Компоненты:

- `Dockerfile`: приложение с Gunicorn и Whitenoise, непривилегированный пользователь;
- `deploy/compose.yaml`: PostgreSQL в именованном томе, приложение доступно только через loopback;
- `deploy/nginx.conf`: доверенный reverse proxy и HTTPS с настоящим сертификатом.

Сборка образа и локальный контейнерный запуск с PostgreSQL проверены. На выбранном VPS отдельно проверяются DNS, настоящий TLS, резервные копии и публичная сеть. Не используйте временный диск или бесплатный спящий экземпляр для единственной рабочей БД.
